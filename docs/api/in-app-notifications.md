# In-app notifications frontend contract

The current repository only contains the frontend implementation. The official API collection in `docu_api_mconnect.json` does not document notification endpoints yet.

The header notification menu is wired to the following expected API shape:

## List notifications

`GET /notifications?limit=10`

Returns either an array, `{ "items": [] }`, or `{ "notifications": [] }`.

Each notification should include:

- `id`
- `tenant_id`, `organization_id`, or `workspace_id`
- `user_id`, when notifications are user-specific
- `type`: `critical_error`, `execution_completed`, or `alert`
- `severity`: `info`, `success`, `warning`, `error`, or `critical`
- `title`
- `message`
- `read_at`
- `created_at`
- `related_entity_type`, optional
- `related_entity_id`, optional

The backend must filter records using the authenticated user and current tenant. Frontend tenant checks are only a defensive UI guard and must not be the security boundary.

## Unread count

`GET /notifications/unread-count`

Returns one of:

```json
{ "count": 3 }
```

```json
{ "unread_count": 3 }
```

If this endpoint is not available, the frontend derives the badge count from the returned notification list.

## Mark as read

`PATCH /notifications/{id}/read`

Marks a single notification as read for the authenticated user. The backend should return `404` when the notification does not exist, belongs to another tenant, or is not visible to the current user.

## Event integration recommendation

Critical errors, completed executions, and alerts should be generated by the same backend event path that powers email or Slack alerts. The frontend should not duplicate event classification logic beyond display labels and icons.
